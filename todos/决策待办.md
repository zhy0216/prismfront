## #1 · Colyseus 是否使用 Schema 承载房间元信息

- **何时需要**：[M0](./done/M00-工程骨架与选型验证.md)（**阻塞**）
- **建议**：不用。绕开 schema 3/4 裂口，联机层也变得可替换
- [x] 已拍板（2026-08-07）—— 结论：**不使用 Schema**。房间元信息（座位 / 阶段 / 计时器）
      与棋盘一样走 `send` / `onMessage`。理由见架构文档 §1.2 风险 A 出路排序第 1 条：
      序列化器版本差异（服务端 `@colyseus/schema@^4` vs `colyseus.js@0.16.22` 的 `^3`）
      随即与我们无关，Colyseus 退化为"带房间、匹配与重连的 WebSocket"，
      连 `colyseus.js` 的 schema 依赖都不会被触发。
      **落地约束**：`apps/server` 不引入 `@colyseus/schema`；Colyseus API 一律包在
      `src/transport/` 之内（[M9](./M09-Colyseus服务端.md) T1 落实）。

      **S1 spike 实测回填（2026-08-07）**：决策成立，`bun run spike:colyseus` 验证
      `serializerId === "none"`，座位表走普通消息下发。该断言是这条不变量的机器可验证哨兵
      —— M9 只要有人写一次 `setState()` 它就当场变红。

      顺带修正了架构文档 §1.1 的一个错误前提：`colyseus.js@0.16.22` 不是"0.17 线的浏览器 SDK
      停在 0.16"，而是 **0.16 线的旧包名**；0.17 线官方 SDK 叫 `@colyseus/sdk`。
      `catalogs.client` 已改为 `@colyseus/sdk@0.17.43`（依赖 `@colyseus/schema@^4.0.7`，
      与服务端同 major），schema 3/4 裂口因此从依赖层面根除，peer 警告消失，适配层删除。
      详见 §1.2 风险 A 的回填块。

## #2 · `initiative` 默认策略

- **何时需要**：[M3](./M03-引擎内核II-回合与同时结算.md) 实现，[M12](./M12-平衡闭环.md) 定
- **建议**：四种全实现走配置；默认先 `alternate`，M12 与 `first_passer` 试玩对比
- [x] 已拍板（2026-08-07）—— 结论：**默认 `alternate`**，四种策略 M3 全部实现走配置。

      重新定位了这条决策的风险：四种策略反正都要实现，"默认"只决定 bot / fuzz / golden
      用哪一套，所以**选错的代价不是返工，是切换时 golden replay 集体失效**。
      因此真正要拍的是两条防线，而不是默认值本身：

      **落地约束**：
      1. golden replay 文件必须**内嵌完整 `RulesConfig` 快照**，不依赖默认值
         （[M8](./M08-bot-CLI-fuzz-golden-replay.md)）。改默认值不该让历史回放全红。
      2. M8 的 golden 集**至少包含一局 `first_passer`**。否则那条码路径会在 M9–M11
         期间烂掉，M12 想做对比试玩时得先修 bug——而那正是最不该有意外的时刻。

      选 `alternate` 而非 `first_passer` 的理由：M3 已经是 ★ 高风险里程碑，
      `first_passer` 让先手规则与 pass 规则耦合，而 pass 同时又是开战触发器；
      在调试同时结算的时候不该再叠一层耦合。M12 之前的平衡数据本来就是丢弃品。

      顺带确认：**首回合先手不是遗留问题**，v2 §36 已定案「首回合随机（消耗 RNG），
      之后每回合轮换」，与 `initiative` 策略正交。

## #3 · `playerActions` 是否开放「移动单位 / 改方向」

- **何时需要**：[M3](./M03-引擎内核II-回合与同时结算.md)
- **建议**：保持默认关（只 `play_card` + `pass`）。开关留着，先跑起来
- [x] 已拍板（2026-08-07）—— 结论：**保持关闭**，`playerActions` 恒为 `["play_card"]`。

      **理由换成色轮论证**，原来的「先跑起来」太弱、经不起以后有人重提：
      `direction` 在 `COLOR_OWNERSHIP` 里是**红 primary / 绿 forbidden**
      （《数值基准》§1.2 方向操作行）。如果每个玩家每回合都能免费改方向，
      红色的主色身份当场蒸发，绿色的禁令也同时失去意义。
      这不是「以后再开」的开关，**开了就得重写 §1.2**——它有资格进风险登记册而不是待办。

      **落地约束**：字段保留在 `RulesConfig` 里（文档诚实），但引擎在**配置校验期
      遇到 `move_unit` / `set_direction` 直接抛错**（M3）。
      不要留一个静默无效的开关——那种坑比没有开关更贵。
      [M7](./M07-视图投影与合法动作.md) 的 `legalActions` 相应只实现
      `play_card` / `pass` 两个分支，不为另两个写死代码（YAGNI）。

## #4 · 卡组同名卡上限 `maxCopies`

- **何时需要**：[M11](./M11-PF1全卡池与lint.md) 前
- **建议**：2（《数值基准》§9 标注待定，纯 `RulesConfig` 随时改）
- [x] 已拍板（2026-08-07）—— 结论：**2**。

      测算支撑：33 张池 × 2 = 66 个槽位里选 30 张，构筑自由度足够（不是"几乎强制"）。
      而稳定性方面，局长 6±1 回合、每局只见 `startingHand 4 + drawPerRound 1 × 6 = 10` 张，
      **同名上限对抽到关键牌的影响远小于牌库大小**
      （2 张时 56%，3 张时 72%，但两者都由"10/30"这个抽牌深度主导）。

      **落地约束**：M12 若发现方差过大，**杠杆是 `deck.size` 或 `drawPerRound`，
      不是 `maxCopies`**——把这条写进 M12 的调参顺序，免得下次先去动同名上限。
      《数值基准》§9 的这一行假设可以标为「已取值，待数据复核」。

## #5 · 蓝英雄塞理安的 3 点预留技能

- **何时需要**：[M11](./M11-PF1全卡池与lint.md)
- **建议**：需要设计定案；不定则先做成纯 3/6 身板
- [x] 已拍板（2026-08-07）—— 结论：**PF1 出纯 3/6 身板，3 点明确登记为「平衡储备」，
      不是「待设计」。**

      核算改变了这条决策的性质：24 点档上**蓝色没有不与绿英雄 4/6 撞车的整数身板**
      ——4/6 恰好 24 但撞绿的「最耐站」定位，3/6 只有 21，3/7 是 23（且血比绿还高，
      更糟）。所以这 3 点**是身板取整的必然残差，不是刻意留的设计位**，
      不必为它硬凑一个技能。

      而且 3 点买不起任何现成效果：《数值基准》§6 的计价里抽 1 = 8 点、眩晕 = 5 点。
      硬要花只能造一个 3 点以下的新效果，等于在没有卡池的时候先猜设计。

      **储备的正式用途**：M12 三色胜率失衡时的**第一个调参杠杆**——它是唯一
      不触碰任何卡牌数据的杠杆，改一行身板即可，回归成本最低。

      **落地约束（重要）**：将来若真要给英雄技能，**必须做成 trigger / intercept 形式，
      不能是主动技**。主动技需要新增一个 player action，直接推翻[决策 #3](#3--playeractions-是否开放移动单位--改方向)，
      要重开那条决策才行。注意蓝色 `aura` 是 forbidden（§1.2 属性增益/光环行），
      所以蓝英雄的被动只能走触发器或拦截器，不能走光环。

## #9 · 卡池按颜色筛选：加 `cond.has_color`，还是给 TagKey 加颜色位？

> M1 实测发现的**真实表达力缺口**，两个独立 agent 各自撞到同一处。

- **何时需要**：[M4](./M04-DSL求值器与首批卡.md)（发现类效果）/ [M11](./M11-PF1全卡池与lint.md)（色轮 lint）
- **背景**：IR v1 §10.5 的「发现」示例用 `cond.has_tag(it, "faction_mage")` 过滤卡池，
  但 v2.1 §11.4 已经用 `card.data.colors` 取代了 `faction` ——
  而当前 93 个 op 里**没有任何一个能按颜色筛卡池**。
  M1 没有自造 op（M1 不该扩词汇表），§10.5 的测试只比对了可表达的那一半并点名说明。
- **两个选项**：
  - 加 `cond.has_color(of, color)` —— 新增 op = minor 版本（IR §8），语义干净
  - 给 `TagKey` 加颜色位 —— 不动 op 集，但把颜色塞进 tag 体系，与 §11.4 的 `data.colors` 重复
- **建议**：加 `cond.has_color`。颜色是卡面数据不是实体 tag，塞进 TagKey 会让
  「色门检查」与「光环改 tag」共用一套管线，语义上讲不通。
- [x] 已拍板（2026-08-07）—— 结论：**加 `cond.has_color`**，IR minor bump（§8：新增 op = minor），
      [M4](./M04-DSL求值器与首批卡.md) 落地。

      **签名对齐 `cond.is_kind`**（不要自创第四种量化形态）：

      ```ts
      | { op: "cond.has_color"; of: Sel; color: Color | Color[] }
      ```

      语义 = `of` 中**每个**成员的 `data.colors` 与参数集合**有交集**
      （`of` 上全称量化、`color` 列表上存在量化，与 `cond.is_kind` 完全一致）。
      推论：**融合卡同时命中它的两个颜色**——"发现一张红牌"应当包含红蓝融合卡，
      这与《数值基准》§6.2「融合卡可跨两色按主色原价取能力」是一致的。
      builder 侧按 §3.3 的惯例提供明确的糖，不要让调用方自己拼全称/存在量化。

      **三条比原建议更硬的理由**（写下来以免以后有人重提 TagKey 方案）：

      1. v2.1 §11.4 把 `colors` 定成**卡面数据（不可变）**，而 Tag 是**实体状态**
         （附魔 / 光环可改）。塞进 TagKey 意味着**一个光环能改一张牌的颜色，
         从而改它的色门合法性**——规则爆炸，且色门是 legality 层不是 DSL 层。
      2. `card.pool` 过滤的是 CardDef 不是场上实体，实体才有 tag。
         而 IR §10.5 的池过滤里 `cond.is_kind` 已经在读 `card.data.kind` 了，
         `has_color` 读 `card.data.colors` 与它**完全平行**；
         作用在场上实体时取该实体源卡的颜色，两种上下文都自洽，不产生新语义。
      3. TagKey 命名空间已被 `COLOR_OWNERSHIP` 的 `direction` 行占用（见 [#10](#10--color_ownership-的非-op-维度如何供-m11-lint-消费)），
         再往里塞颜色，两个 lint 维度会在同一个键空间里打架。

## #10 · `COLOR_OWNERSHIP` 的非 op 维度如何供 M11 lint 消费

> M1 对抗式校验发现：色轮归属表 15 行里有 **5 行没有独占 op**，光按 op 匹配会漏掉三分之一。

- **何时需要**：[M11](./M11-PF1全卡池与lint.md)（色轮越权 lint）
- **背景**：`direction`（方向操作）只能按 **TagKey** 匹配 —— `act.set_tag` / `act.mod_tag`
  是通用节点，同样承载 atk/health，**不能整个 op 归给红**；
  `disable` / `divine_shield` 要按 **FlagName**（`stunned` / `divine_shield`）匹配；
  `growth` / `cleave_siege` / `retaliate` / `aura` 是触发器组合，没有独占 op。
  当前模块只导出了 op 维度的 `ownsOp` / `ownershipOf`，
  tagKey / flag / keyword 三个维度只有 `capabilitiesForXxx` 返回原始行，
  调用方得自己折叠 ownership，容易各写一份。
- **另有一处已知冲突**：`act.buff` 同时落在「属性增益」与「方向操作」两行。
  v2 §8.1 的旗舰红卡 GRID_001 用 `act.buff` 挂 `direction` 附魔，
  按当前 API 会被判到 buff 行（红=secondary，注记「仅加攻」），
  而文档把方向操作判给红 **primary**。M11 直接消费会得出错误计价与错误越权判定。
- **建议**：M11 落 lint 前先补 `ownsTagKey` / `ownsFlag` / `ownsKeyword`，
  并把 `act.buff` 的归属改成「按附魔 mods 的键路由」而不是按 op。
- [x] 已拍板（2026-08-07）—— 结论：**照办，但实现形态改成「露头」判别联合，不是四个平行函数。**

      ### 10a · 查询 API：一次折叠，一条报错路径

      M11 的 lint 是「遍历 IR 树吐出露头 → 逐个判归属 → 拼报错」。
      四个平行的 `ownsTagKey/ownsFlag/ownsKeyword` 会变成四个调用点，
      每个都要自己记得折叠 ownership，正是原分析担心的「各写一份」。
      核心 API 改成：

      ```ts
      type Occurrence =
        | { kind: "op";      op: string }
        | { kind: "tagKey";  tagKey: string }
        | { kind: "flag";    flag: string }
        | { kind: "keyword"; keyword: string };

      ownershipOfOccurrence(color: Color, occ: Occurrence): Ownership | undefined
      ownsOccurrence(color: Color, occ: Occurrence): boolean
      ownershipForColorsOfOccurrence(colors: readonly Color[], occ: Occurrence): Ownership | undefined
      ```

      现有 `ownsOp` / `ownershipOf` / `ownershipForColors` / `colorsOwnOp` 退化成薄包装
      （已有测试，签名不动）。融合卡的多色版本因此只多一个函数而不是多四个。

      ### 10b · `act.buff` 冲突 → 顺带补上一个现存漏洞

      原分析说的冲突成立，而且比记录的更严重：`buff` 行按 op 匹配 `act.buff`，
      于是 **`act.set_tag(友军, "atk", 10)` 完全绕过色轮**——
      蓝色（属性增益 = forbidden）**今天就能这么写而 lint 放行**。

      **修法**：把 `"act.buff"` 从 `buff` 行的 `ops` 里摘掉，该行改按
      `tagKeys: ["atk", "health"]` 匹配，与 `direction` 行同构。于是
      `act.buff` / `act.set_tag` / `act.mod_tag` 三个通用 op **统一按 tag 键路由**：

      - GRID_001 的方向附魔自动落到 `direction` 行 = 红 **primary**（原价），
        不再被误判成 buff 行的 secondary + 「仅加攻」注记；
      - 上面那个 `set_tag` 漏洞同时补上。

      `buff` 行的 `keywords: ["aura"]` 不动（光环是 Card 的 `auras` 段，本来就不是 op）。

      **前置依赖，必须写进 M11**：`act.buff` 只带 `ench: EnchantId`（不是内联 mods），
      所以**色轮 lint 必须以整个 `Bundle`（含 `enchantments` 表）为输入**，
      不能只看单卡的 IR 树——附魔的 `mods` 键在另一个文档里。

      ### 10c · 衍生问题：属性「减益」是否受色轮约束 → **不受，放行**

      按 tag 键路由之后会连带把「把 atk/health 调成负值」判进蓝色禁区，
      而**减敌方攻击力是非常蓝的控制效果**。拍板：

      **`buff` 行的匹配条件加符号判据 —— `tagKey ∈ {atk, health}` 且 **值 > 0**。**
      负值改动落到「未登记」= 不受色轮约束，与 `color-ownership.ts` 现有的
      「表是黑名单不是白名单」原则一致，不动《数值基准》§1.2 文档。

      ```
      act.buff(友军, +2/+2)      → buff 行，蓝禁 ✓
      act.buff(敌方, -2/-0)      → 未登记，放行
      act.set_tag(友军, atk, 10) → buff 行，蓝禁 ✓（补上现存漏洞）
      act.buff(自身, direction)  → direction 行，红 primary ✓（修正误判）
      ```

      **已知残留**：绿色因此可以自由减敌方攻击力，而绿本该没有直接解牌手段
      （它的解牌是决斗）。这不是 lint 能挡的，只能靠 M11 写卡时自律 +
      M12 的胜率数据兜底。**已登记进[风险登记册](./风险登记册.md)**，
      若 M12 发现绿因此过强，再给 §1.2 补一行「属性减益」（红副/蓝主/绿禁）
      并为减益定价——那是文档变更，届时重开本条。
