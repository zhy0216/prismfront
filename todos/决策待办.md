## #1 · Colyseus 是否使用 Schema 承载房间元信息

- **何时需要**：[M0](./done/M00-工程骨架与选型验证.md)（**阻塞**）
- **建议**：不用。绕开 schema 3/4 裂口，联机层也变得可替换
- [x] 已拍板（2026-08-07）—— 结论：**不使用 Schema**。房间元信息（座位 / 阶段 / 计时器）
      与棋盘一样走 `send` / `onMessage`。理由见架构文档 §1.2 风险 A 出路排序第 1 条：
      序列化器版本差异（服务端 `@colyseus/schema@^4` vs `colyseus.js@0.16.22` 的 `^3`）
      随即与我们无关，Colyseus 退化为"带房间、匹配与重连的 WebSocket"，
      连 `colyseus.js` 的 schema 依赖都不会被触发。
      **落地约束**：`apps/server` 不引入 `@colyseus/schema`；Colyseus API 一律包在
      `src/transport/` 之内（[M9](./M09-Colyseus服务端.md) T1 落实）。

      **S1 spike 实测回填（2026-08-07）**：决策成立，`bun run spike:colyseus` 验证
      `serializerId === "none"`，座位表走普通消息下发。该断言是这条不变量的机器可验证哨兵
      —— M9 只要有人写一次 `setState()` 它就当场变红。

      顺带修正了架构文档 §1.1 的一个错误前提：`colyseus.js@0.16.22` 不是"0.17 线的浏览器 SDK
      停在 0.16"，而是 **0.16 线的旧包名**；0.17 线官方 SDK 叫 `@colyseus/sdk`。
      `catalogs.client` 已改为 `@colyseus/sdk@0.17.43`（依赖 `@colyseus/schema@^4.0.7`，
      与服务端同 major），schema 3/4 裂口因此从依赖层面根除，peer 警告消失，适配层删除。
      详见 §1.2 风险 A 的回填块。

## #9 · 卡池按颜色筛选：加 `cond.has_color`，还是给 TagKey 加颜色位？

> M1 实测发现的**真实表达力缺口**，两个独立 agent 各自撞到同一处。

- **何时需要**：[M4](./M04-DSL求值器与首批卡.md)（发现类效果）/ [M11](./M11-PF1全卡池与lint.md)（色轮 lint）
- **背景**：IR v1 §10.5 的「发现」示例用 `cond.has_tag(it, "faction_mage")` 过滤卡池，
  但 v2.1 §11.4 已经用 `card.data.colors` 取代了 `faction` ——
  而当前 93 个 op 里**没有任何一个能按颜色筛卡池**。
  M1 没有自造 op（M1 不该扩词汇表），§10.5 的测试只比对了可表达的那一半并点名说明。
- **两个选项**：
  - 加 `cond.has_color(of, color)` —— 新增 op = minor 版本（IR §8），语义干净
  - 给 `TagKey` 加颜色位 —— 不动 op 集，但把颜色塞进 tag 体系，与 §11.4 的 `data.colors` 重复
- **建议**：加 `cond.has_color`。颜色是卡面数据不是实体 tag，塞进 TagKey 会让
  「色门检查」与「光环改 tag」共用一套管线，语义上讲不通。
- [ ] 已拍板 —— 结论：

## #10 · `COLOR_OWNERSHIP` 的非 op 维度如何供 M11 lint 消费

> M1 对抗式校验发现：色轮归属表 15 行里有 **5 行没有独占 op**，光按 op 匹配会漏掉三分之一。

- **何时需要**：[M11](./M11-PF1全卡池与lint.md)（色轮越权 lint）
- **背景**：`direction`（方向操作）只能按 **TagKey** 匹配 —— `act.set_tag` / `act.mod_tag`
  是通用节点，同样承载 atk/health，**不能整个 op 归给红**；
  `disable` / `divine_shield` 要按 **FlagName**（`stunned` / `divine_shield`）匹配；
  `growth` / `cleave_siege` / `retaliate` / `aura` 是触发器组合，没有独占 op。
  当前模块只导出了 op 维度的 `ownsOp` / `ownershipOf`，
  tagKey / flag / keyword 三个维度只有 `capabilitiesForXxx` 返回原始行，
  调用方得自己折叠 ownership，容易各写一份。
- **另有一处已知冲突**：`act.buff` 同时落在「属性增益」与「方向操作」两行。
  v2 §8.1 的旗舰红卡 GRID_001 用 `act.buff` 挂 `direction` 附魔，
  按当前 API 会被判到 buff 行（红=secondary，注记「仅加攻」），
  而文档把方向操作判给红 **primary**。M11 直接消费会得出错误计价与错误越权判定。
- **建议**：M11 落 lint 前先补 `ownsTagKey` / `ownsFlag` / `ownsKeyword`，
  并把 `act.buff` 的归属改成「按附魔 mods 的键路由」而不是按 op。
