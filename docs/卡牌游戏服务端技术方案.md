# 卡牌游戏服务端设计技术方案

## 0. 先分清游戏类型（这决定了 80% 的架构）

| 类型 | 代表 | 服务端压力核心 | 架构倾向 |
|---|---|---|---|
| 强对抗 PvP 集换式 | 炉石、影之诗、昆特牌 | 战斗逻辑权威性、防作弊、匹配 | 服务端全权威战斗服 + Actor 房间 |
| 数值卡牌 RPG | 阴阳师、明日方舟、剑与远征 | 数据一致性、抽卡、活动运营 | 重后台 CRUD + 战斗校验/重放 |
| 棋牌房间制 | 斗地主、麻将 | 房间管理、断线重连、反作弊 | skynet/Actor 房间制成熟方案 |
| 带经济系统的 TCG | MTG Arena、Gods Unchained | 交易撮合、资产确权、审计 | 加交易服 + 强幂等 + 流水审计 |

后面的方案默认覆盖前三类，第四类在"存储与幂等"一节单独说。

---

## 1. 通用分层架构

```
客户端 (Unity / Cocos / H5)
   │  WebSocket + Protobuf
   ▼
┌──────────────┐
│  Gateway     │  长连接接入、会话管理、协议编解码、限流、心跳
└──────┬───────┘
       │ 内部 RPC (gRPC / 自研)
   ┌───┴────┬──────────┬──────────┬─────────┐
   ▼        ▼          ▼          ▼         ▼
 Lobby   Match      Battle      Shop     Social
 大厅服  匹配服    战斗服(有状态) 商城/抽卡  社交/公会
   │        │          │          │         │
   └────────┴─────┬────┴──────────┴─────────┘
                  ▼
      Redis (热数据/会话/排行/分布式锁)
      MySQL / MongoDB (持久化)
      Kafka / NATS (事件流、日志、跨服异步)
      ClickHouse (抽卡流水、对局日志、BI)
```

**协议层默认答案：WebSocket + Protobuf。**
卡牌游戏是低频强逻辑（一个操作几百毫秒到几秒一次），不需要 UDP/KCP/帧同步那套；WebSocket 能同时覆盖 H5、小程序、移动端、PC，是性价比最高的选择。Protobuf 省带宽且有强 schema，比 JSON 更适合长期演进。

## 2. 战斗权威模型：三选一

这是最核心的架构决策。

### A. 服务端全权威（Server-authoritative）
服务端跑完整战斗逻辑，客户端只发操作指令、收事件流播动画。

- 优点：最安全，PvP 唯一正确选择。炉石、MTG Arena 都是这个模式。
- 代价：服务端要实现一整套战斗逻辑（重复投入）；CPU 与内存成本；开发周期长。
- 适用：所有 PvP 对战、排位赛、有经济价值的对局。

### B. 客户端计算 + 服务端确定性重放校验
客户端本地跑战斗，上传操作序列 + 随机种子 + 结果；服务端用同一份确定性逻辑重放，比对结果，不一致则判定作弊。

- 优点：服务端成本低（可以异步/抽样校验），开发上可以复用同一份逻辑代码。
- 前提：**逻辑必须完全确定性**（见第 3 节）。
- 适用：PvE 关卡、异步 PvP（打对方防守阵容）。数值卡牌 RPG 的主流做法。

### C. 客户端权威 + 抽检
客户端直接上报结果，服务端只做合理性区间校验。

- 只适合纯单机 PvE 且无高价值奖励的场景。有排行榜/交易就一定会被刷。

**实践建议**：PvP 用 A，PvE 用 B，永远不要在有奖励的地方用 C。

---

## 3. 确定性（Determinism）——卡牌游戏最容易翻车的工程点

只要你用了模式 B，或者要做录像回放/观战，确定性就是硬需求。踩坑清单：

1. **随机数**：服务端下发种子，双端用同一个 PRNG（xorshift128+ / PCG），禁止用语言自带的 `Random`（各语言实现不同）。抽卡、随机目标、"发现"三选一，每个随机点都要可复现。
2. **禁用浮点**：伤害计算、暴击率、百分比减伤全部用整数或定点数（如放大 10000 倍的 int64）。浮点在不同 CPU/编译器/JIT 下结果可能不一致。
3. **容器遍历顺序**：Go 的 `map` 遍历是随机的，C# 的 `Dictionary` 顺序不保证。所有参与逻辑的集合必须用有序结构（slice / List + 显式排序）。
4. **对象 ID 分配**：实体 ID 必须由确定的自增器分配，不能用地址、哈希、时间戳。
5. **时间**：逻辑层不允许读系统时间，只能用回合数/逻辑帧号。
6. **逻辑与表现彻底分离**：动画时长、特效播放绝不能影响逻辑推进。

## 4. 卡牌效果系统设计（卡牌游戏最独特、最值钱的部分）

这是卡牌服务端真正的技术难点，不是网络也不是并发，是**领域建模**。

### 4.1 四种实现路线

| 路线 | 描述 | 优 | 劣 |
|---|---|---|---|
| 硬编码 + 注册表 | 每张卡一个 handler 类/函数 | 直观、好调试、性能最好 | 出卡速度慢，程序员是瓶颈 |
| 数据驱动原子效果 | 效果拆成原子（伤害/抽牌/召唤/加Buff/改属性），卡 = 原子组合 + 参数，策划配表 | 出卡快、策划自助、易平衡性调整 | 原子库设计难，怪卡表达不了 |
| 脚本化（Lua/JS） | 每张卡一段脚本 | 表达力最强、热更新友好 | 无类型易出 bug、需要沙箱与性能预算 |
| ECS + 事件总线 | 卡 = 实体，效果 = 事件监听器 | 复杂连锁天然支持 | 调试困难、心智负担高 |

**推荐组合方案**：原子效果库（覆盖 ~80% 卡）+ 触发器/时机系统 + 少量脚本兜底（怪卡）。这是行业里最稳的折中。

### 4.2 触发器与结算顺序（最容易出 bug 的地方）

亡语、连锁触发、光环重算的顺序问题，会在上线后持续产出线上 bug。必须在第一天就定死规则：

- **用事件队列，不要用递归调用**。效果 A 触发效果 B，B 不能在 A 的调用栈里直接执行，而是入队，等 A 完整结算后按序出队。否则连锁三层以上必乱。
- **触发器注册顺序即执行顺序**（通常按"先我方后敌方、场上从左到右"），明文写进设计文档。
- **光环 / 持续效果用"全量重算"而非"增量修改"**。每次场面变化后重新计算所有单位的最终属性 = 基础值 + 所有生效光环。增量加减会在光环消失、单位死亡、复制效果等场景下累积错误，这是经典事故源。
- **状态基础动作（State-Based Actions）**：借鉴 MTG——每次效果结算完，统一检查"血量 ≤ 0 的单位死亡""超过手牌上限弃牌"等，而不是散落在各个效果里判断。

### 4.3 事件流即协议
服务端产出的事件流应当能**完整重建整个战局**：

```
GameStart{seed, players, decks}
DrawCard{player:1, cardInstanceId:37, cardId:"CS2_005"}
PlayCard{player:1, instanceId:37, target:null, cost:2}
  → Damage{source:37, target:52, amount:3}
  → Death{entity:52}
  → Trigger{source:52, effect:"deathrattle"}
TurnEnd{player:1}
```

这一套事件流同时解决四件事：客户端播放、断线重连补发、观战、录像回放。设计时就按"可重放"的标准来做。

### 4.4 视图裁剪（防外挂的第一道也是最重要的一道防线）

**服务端下发给每个玩家的事件流必须做 per-player 裁剪**：对手抽到的牌，下发的应是 `DrawCard{player:2, instanceId:88, cardId:HIDDEN}`。

这是卡牌游戏最高频的外挂类型——抓包看对手手牌/牌库顺序。如果服务端图省事把完整状态广播给双方由客户端隐藏，等于没有防护。观战和录像同样要按延迟/裁剪策略处理。

## 5. 对局管理：Actor 模型

**一个对局 = 一个 Actor（goroutine / Orleans Grain / Erlang process / skynet service）**，串行处理该对局的所有消息。

- 好处：房间内完全无锁，逻辑代码写成单线程风格，确定性也更容易保证。
- 状态在内存，**关键节点（回合结束、重要效果结算后）快照到 Redis**，用于服务器崩溃恢复和跨进程迁移。
- 路由：Gateway 需要把玩家消息路由到正确的战斗服进程——用一致性哈希 + 对局 ID 映射表（存 Redis），或走会话粘性。
- 超时保护：每个操作有倒计时，超时自动跳过/托管，防止挂机拖死房间。

---

## 6. 断线重连

必须在架构初期就设计，后补代价极大。

1. 断线后服务端保留对局状态 N 分钟（通常 3–5 分钟，超时判负或托管 AI）。
2. 重连时下发**裁剪后的完整战局快照** + 之后的增量事件。
3. 客户端与服务端维护事件序列号 `seq`，重连时上报"我收到了第几号"，服务端从该点补发。
4. 客户端要能"瞬间快进"——把补发的事件流无动画地快速结算到最新状态。

## 7. 匹配系统

- **评分算法**：ELO 够用；Glicko-2 / TrueSkill 更准（考虑评分可信度、长期不玩的衰减）。
- **匹配策略**：分段队列 + 随等待时间放宽的匹配区间；加入新手保护、连败补偿、避免连续遇到同一对手。
- **实现**：小规模用 Redis ZSET；上量后独立匹配服在内存里维护候选池，定时（如每 500ms）批量撮合，比逐个匹配效果好得多。
- **卡组克制维度**：进阶做法是在匹配中加入卡组原型（archetype）特征，避免天克局体验。

---

## 8. 存储与幂等

- **玩家数据**：Redis 作热缓存（定时 + 关键点写回）+ MySQL 持久化；或直接用 MongoDB（文档模型天然适配玩家档案）。
- **卡组存储**：卡牌 ID + 数量的紧凑编码（可位压缩成短字符串，方便分享卡组码）。
- **幂等是红线**：抽卡、购买、发奖、体力消耗必须携带客户端生成的事务 ID，服务端去重。网络重试导致的重复扣费/重复发奖是最常见的线上事故与客诉来源。
- **流水审计**：所有货币变动、抽卡结果写入独立日志（Kafka → ClickHouse）。用途：客服查证、概率公示合规（国内要求公示抽卡概率）、数值分析、作弊追查。
- **保底逻辑**：抽卡保底计数器必须与抽卡操作在同一事务内更新，否则会被并发请求刷穿。

---

## 9. 反作弊清单

1. 服务端权威（PvP）/ 确定性重放校验（PvE）。
2. **视图裁剪**——见 4.4，最重要。
3. **操作合法性校验**：这张卡在当前状态能不能打？法力值够不够？目标合法吗？现在是不是你的回合？每一条都要在服务端查，不能信客户端。
4. 频率与异常检测：不可能的操作速度、异常胜率、异常掉落分布。
5. 协议签名 + 序列号防重放；敏感接口加设备/风控标识。

---

## 10. 热更新与版本管理

- **配置热更**：卡牌数值、掉落、活动参数走配置表，带版本号，支持不停服下发。卡牌游戏改数值的频率极高，这是必需品。
- **逻辑热更**：Lua/JS 脚本层天然支持；Go/Java 需要靠灰度重启 + 平滑下线（等待存量对局结束后再重启该战斗服实例）。
- **版本隔离**：一局对战中途绝不能切换规则版本；匹配时要保证双方客户端版本兼容，灰度期间按版本分池匹配。

## 11. 技术栈选型对比

| 技术栈 | 代表框架 | 优势 | 劣势 |
|---|---|---|---|
| **Go** | Pitaya、Leaf、Nano、自研 | goroutine 天然映射连接与房间；GC 停顿低；单二进制部署简单；招人容易；云原生生态好 | 无法与 Unity 客户端共享战斗逻辑（要写两遍）；表达力偏弱，写复杂效果系统略啰嗦；map 遍历随机需特别注意确定性 |
| **C# / .NET** | ET 框架、Orleans、MagicOnion | **能与 Unity 客户端共享同一份战斗逻辑代码**——这对卡牌游戏是压倒性优势；Orleans 虚拟 Actor 直接对应"一局一 Actor" | 国内运维生态弱于 Go/Java；ET 框架有学习曲线；容器化部署经验相对少 |
| **Lua + C (skynet)** | skynet | Actor 模型天然契合房间制；热更新能力最强；国内棋牌/卡牌行业验证极充分 | Lua 无静态类型，大型项目维护成本高；招人面窄 |
| **Java** | Netty + Spring、自研 | 中间件与运营后台生态最完整；适合重后台（商城、活动、公会、运营工具） | 内存占用高、GC 需调优；做战斗服偏重 |
| **Erlang / Elixir** | OTP、Phoenix | Actor + 监督树，容错与热更新的天花板 | 团队稀缺；数值密集计算弱 |
| **Node / TypeScript** | Colyseus | 与 H5/小程序/Cocos 共享 TS 逻辑；MVP 速度最快 | 单线程 CPU 上限低；上规模需要多进程编排 |
| **Rust** | tokio 自研 | 性能与内存安全 | 生态不成熟、开发慢；卡牌游戏本身不是性能瓶颈型，收益不明显 |

**选型的第一原则**：卡牌游戏的最大隐性成本是**战斗逻辑双端重复实现导致的不一致 bug**。如果客户端是 Unity，C# 服务端能共享逻辑代码，这个收益往往超过 Go 在运维和性能上的优势。

## 12. 三套推荐组合

**① Unity 客户端 + 中小团队（推荐度最高）**
C# / .NET 8 + Orleans（或 ET 框架）+ Redis + MySQL + Protobuf/WebSocket
→ 战斗逻辑一套代码双端跑，Orleans Grain 天然是"一局一 Actor"，开发效率最高，确定性最容易保证。

**② 中大型团队 / 强运维要求**
Go（Pitaya 或自研）+ gRPC 内部通信 + Redis + MySQL + Kafka + K8s
→ 生态成熟、扩容运维顺手、招人容易。代价是战斗逻辑要单独实现一份，需要用配置驱动 + 严格的一致性测试（同一批操作序列跑双端 diff）来兜底。

**③ 棋牌 / 强房间制 / 需要极致热更**
skynet（Lua）+ Redis + MySQL
→ 房间 actor 模型契合度最高、热更新最强、行业方案成熟，出问题网上有大量参考。

**④ 快速验证 MVP**
Node/TS + Colyseus + Redis
→ 两周能跑通对战原型，验证玩法后再决定是否重写。

## 13. 容量与性能量级参考

- 单次卡牌操作的服务端计算通常在**亚毫秒到几毫秒**量级，一局对战的内存占用在**几十到几百 KB**。卡牌游戏的战斗计算基本不构成瓶颈。
- 真正的压力点是：**登录风暴**（开服/维护后）、**抽卡峰值**（新卡池上线时的数据库写入）、**活动结算**（定时任务集中写）、**排行榜更新**。这几处才需要重点做限流、削峰和缓存。
- 具体承载量必须以你的效果系统实现和快照策略实测为准，上线前做全链路压测，尤其是抽卡与登录这两条路径。

---

## 14. 落地顺序建议

1. 先定义**事件流协议**和**效果原子库**——这两个是地基，改起来最贵。
2. 写一个**纯逻辑的战斗内核**（不含网络、不含数据库），用单元测试驱动，能跑完整对局。
3. 套上 Actor 房间层和 Gateway。
4. 接断线重连（用第 1 步的事件流，成本很低）。
5. 再做匹配、商城、活动这些外围。

把战斗内核做成零依赖的纯函数式模块，是卡牌服务端最值得的一笔前期投资——它让确定性测试、双端一致性校验、录像回放、AI 托管全都变得廉价。
