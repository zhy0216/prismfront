# 数字卡牌引擎市场调研

> 调研日期：2026-07-31  
> 口径：面向数字卡牌、TCG/CCG、牌组构筑游戏；同时覆盖专用模板、开源规则框架、托管创作平台、联机后端和可借鉴的完整开源游戏。价格与版本均为调研当日快照。

## 一页结论

1. **市场上没有一款跨技术栈、规则通用、生产级且占据主导地位的“卡牌游戏引擎”。** 实际供给分成商业整包模板、开源规则/UI 框架、托管创作平台、通用联机后端四层。
2. **Unity 商业模板最接近开箱即用。** 在线 CCG 首选比较 TCG Engine 与 CCG Kit；单机牌组构筑可看 Single-Player CCG Kit；Card Game Core 适合低成本验证。
3. **Godot 生态正在增长，但现代方案仍是拼装式。** Card Framework 主要解决卡牌交互和 UI；Card Combat Engine 主要解决规则和战斗，两者组合方向合理，但后者刚发布且标记为不稳定。
4. **Web 端最成熟的通用选择是 boardgame.io，而不是专用 TCG 引擎。** 它解决状态、回合、阶段、多人同步和日志，但卡牌技能 DSL、隐藏信息策略、收藏经济和内容编辑器仍需自建。
5. **Dulst、VASSAL 适合验证玩法，不适合直接替代自有产品引擎。** Dulst 是托管式无代码平台；VASSAL 更像传统桌游/卡牌的远程桌面。
6. **如果目标是建设自己的 `card-game-engine`，市场空缺是“确定性、无头、跨前端、服务器权威的规则内核”。** 前端渲染和账号/匹配可以接现有生态，真正值得自研的是状态模型、合法动作、触发器、隐藏信息、回放、内容 DSL 与批量模拟。

## 市场分层

| 层级 | 解决的问题 | 代表产品 | 不负责什么 |
|---|---|---|---|
| 成品模板 | 客户端、规则样例、UI、部分后端和商业系统 | TCG Engine、CCG Kit、Single-Player CCG Kit | 通常不保证适配完全不同的规则 |
| 规则/UI 框架 | 状态、回合、卡牌交互、规则脚本 | boardgame.io、Godot Card Game Framework、Card Framework、Card Combat Engine | 通常没有完整账号、经济、运营后台 |
| 托管创作平台 | 无代码编辑、托管、匹配、社区 | Dulst、VASSAL | 通常不能作为独立产品技术底座 |
| 联机后端 | 账号、存储、匹配、排行榜、权威对局承载 | Nakama、Colyseus | 不自带卡牌规则 |
| 模拟/参考实现 | AI、平衡性、复杂规则实现参考 | OpenSpiel、RLCard、XMage、OpenDuelyst | 不等于可直接发行的通用引擎 |

## 主要候选

### 1. Unity 商业模板

#### [TCG Engine – Online Card Game](https://assetstore.unity.com/packages/templates/systems/tcg-engine-online-card-game-253269)

- 技术：Unity/C#；Unity Netcode for GameObjects；可选 Node.js + MongoDB Web API。
- 当日价格与版本：99 美元，v1.15，最近发布于 2025-09-22。
- 覆盖：单机和多人、权威专用服务器、匹配、登录、玩家数据库、收藏、开包、货币、排行榜、好友、Minimax AI；Unity 6+ 支持 WebGL。
- 优点：扫描到的方案中，产品闭环最完整，适合快速做在线 CCG MVP。
- 风险：本质是完整模板而不是中立规则内核；规则明显偏常见的“费用—随从—攻击—生命”模型，复杂改造需要修改源码；受 Unity Asset Store EULA 和 Unity 网络栈约束。

#### [CCG Kit](https://assetstore.unity.com/packages/templates/systems/ccg-kit-52739)

- 技术：Unity/C#；Mirror Networking；包含 Dedicated Server Kit 集成。
- 当日价格与版本：199.99 美元，v3.1.0，最近发布于 2026-07-22。
- 覆盖：服务器权威多人对局、专用服务器、可视化卡牌数据编辑、示例 CCG 规则。
- 优点：历史较长，已从废弃的 UNET 迁移到 Mirror；服务端权威模型比纯客户端模板更适合竞技游戏。
- 风险：价格较高；与 Mirror 和 Unity 工程结构耦合；仍需要先验证复杂卡牌效果、断线重连、观战、回放和内容热更新是否满足目标。

#### [Single-Player CCG Kit](https://assetstore.unity.com/packages/templates/systems/single-player-ccg-kit-150156)

- 技术：Unity/C#，URP，依赖 DOTween。
- 当日价格与版本：199.99 美元，v1.5.0，最近发布于 2026-07-22。
- 覆盖：偏《杀戮尖塔》的单机牌组构筑流程，包含地图、战斗、卡牌/角色/敌人编辑和完整源码。
- 优点：单机 PvE 闭环比从在线 TCG 模板反向裁剪更合适。
- 风险：对玩法范式约束较强；高级卡牌能力仍要编码；不是联机底座。

#### [Card Game Core](https://assetstore.unity.com/packages/templates/systems/card-game-core-tcg-ccg-system-with-deck-builder-284361)

- 技术：Unity/C#，依赖 DOTween 与 Extenject。
- 当日价格与版本：9.99 美元，v2.4.2，最近发布于 2026-02-13。
- 覆盖：基础 TCG/CCG 对局、AI、牌组构筑、卡牌/法术/英雄和视觉动画。
- 优点：采购成本低，适合做短期技术验证或研究模板结构。
- 风险：基础版不应被当成完整在线产品；多人 PvP 是另一产品线；生态与评价样本显著小于 TCG Engine/CCG Kit。

### 2. 开源规则与交互框架

#### [boardgame.io](https://github.com/boardgameio/boardgame.io)

- 技术：TypeScript/JavaScript，MIT。
- 能力：用纯状态转换函数定义动作；自动管理客户端/服务端状态、多人同步、阶段、回合顺序、Lobby、基础 AI、日志与时间旅行；不绑定 React。
- 成熟度：约 1.2 万 GitHub Star。仓库在 2026 年重新出现活跃提交，但 npm 稳定版仍是 2022 年发布的 0.50.2，采用前应检查新版本发布计划。
- 优点：抽象干净，最适合 Web 原型，也很适合作为自研规则 API 的参考。
- 缺口：没有专用卡牌技能 DSL、收藏/开包/经济、卡牌编辑器；复杂隐藏信息、效果栈和内容版本兼容需要项目层实现。

#### [Godot Card Game Framework](https://github.com/db0/godot-card-game-framework)

- 技术：Godot 3/GDScript，AGPL-3.0，另有 Steam/Steamworks 分发附加条款。
- 能力：手牌、牌堆、拖放、目标箭头、附着、翻面、Token、牌库、组牌器，以及基于字典/纯文本的卡牌脚本和触发器。
- 成熟度：约 1.4k Star；正式版 2.2.0 发布于 2022 年，最近一次提交为 2025 年的文档更新。
- 优点：专用卡牌功能覆盖较广，规则脚本设计值得研究。
- 风险：Godot 3 兼容性和维护节奏是主要问题；AGPL 对闭源和服务器端商业使用不友好，需单独做法律评估。

#### [Card Framework](https://github.com/chun92/card-framework)

- 技术：Godot 4.6+/GDScript，MIT。
- 当前版本：v1.4.0，发布于 2026-05-08。
- 能力：拖放、牌堆、扇形手牌、JSON 卡牌数据、编辑器预览、移动历史、扩展容器和完整 FreeCell 样例。
- 优点：现代 Godot、许可宽松、交互/UI 层职责清晰。
- 缺口：它是卡牌表现与容器框架，不是 TCG 规则引擎，也不含联机和运营系统。

#### [Card Combat Engine](https://github.com/JavierIslas/Card-Combat-System)

- 技术：Godot 4.6+/GDScript；AGPL-3.0 或单独商业许可。
- 能力：无头战斗逻辑、回合状态机、费用、抽牌、攻击/防御/阻挡、同时伤害、可插拔 AI、确定性随机、序列化、指令日志、多阵营/队伍；官方宣称有 418 个单元测试。
- 优点：架构方向与生产级卡牌规则内核接近，可与 Card Framework 配对。
- 风险：2026 年 6 月才出现，约 10 Star、无用户评价，Godot 商店将版本标记为不稳定；只能作为试验候选，不能仅凭功能清单直接押注生产。

#### 新兴规则模拟项目

- [TCGEngine](https://github.com/TCG-Engine/TCGEngine)：MIT，PHP 为主，2026 年仍高频提交；包含通用模拟器、卡牌编辑器、AI/MCP 工具和多个现实 TCG 的实现。项目很新、社区很小，适合研究卡牌数据和模拟工具链，不宜直接当生产 SDK。
- [TheCardGoat/tcg-engines](https://github.com/TheCardGoat/tcg-engines)：MIT、TypeScript，公开了 Lorcana、Cyberpunk、Gundam、One Piece 等游戏规则工作区和共享模拟器契约；生产 Web/API/匹配/基础设施仍为私有，当前更像规则实现参考集合。

### 3. 无代码与传统桌游平台

#### [Dulst](https://dulst.com/)

- 形态：浏览器托管的无代码卡牌游戏创作与发行平台。
- 能力：可视化棋盘、效果和规则编辑；HTML5 多人、免费匹配、自动单机 AI、等级、成就、市场、卡牌购买与合成、论坛和聊天。
- 当日价格：免费层；Pro 49 美元/月；Enterprise 499 美元/月。
- 适合：非程序策划快速做完整玩法验证，或小规模社区测试。
- 不适合：要求自托管、跨端原生体验、底层规则完全可控或避免平台锁定的正式产品。

#### [VASSAL](https://vassalengine.org/about.html)

- 形态：Java 编写的开源传统桌游/卡牌远程化引擎，LGPL-2.1+。
- 能力：模块编辑器、牌堆、手牌、隐藏信息、实时联网和邮件对局；拥有大量传统桌游模块。
- 适合：把实体卡牌快速搬到线上进行人工规则测试。
- 不适合：现代商业 CCG 客户端、强规则自动执行、移动端原生体验和独立品牌发行。

### 4. 可组合的联机后端

#### [Nakama](https://github.com/heroiclabs/nakama)

- Apache-2.0，Go 编写；服务端逻辑可用 Go、TypeScript/JavaScript 或 Lua。
- 自带账号、存储、好友/群组、聊天、匹配、权威/中继多人、排行榜、锦标赛、通知和购买校验。
- 更适合需要完整玩家平台和 LiveOps 的产品；卡牌规则仍需在自定义服务端运行时实现。

#### [Colyseus](https://github.com/colyseus/colyseus)

- MIT，Node.js/TypeScript。
- 提供权威 Room、自动增量状态同步、匹配、重连和 Redis 横向扩展。
- 更适合 TypeScript 团队快速搭建权威对局服务器；账号、经济、运营能力不如 Nakama 一体化。

## 值得研究但不应直接叫“通用引擎”的项目

- [OpenDuelyst](https://github.com/open-duelyst/duelyst)：完整数字 CCG + 战棋产品源码，包含客户端、服务端、Worker、测试、Docker 和 Terraform，CC0-1.0。非常适合研究完整产品边界，但技术栈偏旧、规则强绑定 Duelyst。
- [XMage](https://github.com/magefree/mage)：Java 客户端/服务器，实现 31,000 多张独特 MTG 卡牌、完整规则、AI、牌组编辑和赛事。它是复杂触发器、替代效应、优先权和海量卡牌测试的宝贵参考，但不是中立 SDK。
- [OpenSpiel](https://github.com/google-deepmind/open_spiel)：Apache-2.0，C++/Python，面向一般博弈、搜索、强化学习和不完全信息游戏。
- [RLCard](https://github.com/datamllab/rlcard)：MIT，Python，面向扑克、斗地主、UNO、麻将等卡牌环境和强化学习。
- 后两者适合 AI、平衡性和批量模拟，不负责正式游戏的 UI、联机和商业系统。

## 按场景选型

| 场景 | 第一批应试方案 | 判断 |
|---|---|---|
| 最快做在线 1v1 CCG MVP | TCG Engine、CCG Kit | TCG Engine 产品闭环更全；CCG Kit 的 Mirror 权威服务器路线更明确 |
| 做单机牌组构筑/PvE | Single-Player CCG Kit、Card Game Core | 前者闭环完整，后者适合便宜验证 |
| Godot 4 新项目 | Card Framework + 自研规则核；试验 Card Combat Engine | 不建议把 UI 插件误判为规则引擎 |
| Web 优先、团队擅长 TS | boardgame.io；或自研规则核 + Colyseus | boardgame.io 上手快，自研组合的长期控制力更强 |
| 无代码验证玩法 | Dulst | 快，但要接受托管平台边界 |
| 把实体卡牌搬到线上测试 | VASSAL | 更接近远程桌面，不追求商业客户端体验 |
| 做 AI/自动平衡 | OpenSpiel、RLCard，自研无头模拟器 | 与正式客户端解耦 |
| 建设可复用的卡牌引擎产品 | 自研确定性规则核 + Nakama/Colyseus + 多前端适配器 | 市面上的现成产品在这一层仍有明显空缺 |

## 对自研引擎的产品机会判断

如果目标不是做一款具体游戏，而是做可复用引擎，建议将边界定在：

```text
卡牌内容 Schema / DSL
        ↓
确定性无头规则内核
        ↓
合法动作、隐藏视图、事件日志、快照、回放、模拟
        ↓
服务端权威适配器 ── Nakama / Colyseus / 自建
        ↓
Unity / Godot / Web 客户端适配器
```

最有差异化价值的能力：

1. 确定性 RNG、命令日志、快照和逐版本回放。
2. `legalActions(state, player)`，使 UI、服务器校验、AI 和测试共用同一规则。
3. 对不同玩家生成脱敏视图，原生支持手牌、牌库顺序和秘密效果。
4. 触发器、替代效应、响应窗口、效果栈和明确的结算顺序。
5. 卡牌内容 DSL、版本迁移、热更新约束和静态校验。
6. 无渲染依赖的批量模拟、AI 接口和性能基准。
7. Golden replay、属性测试、模糊测试和复杂卡牌组合回归。
8. 前端只消费状态差异和领域事件，不拥有最终规则。

不建议优先自研的外围能力：

- 账号、好友、聊天、排行榜、通用匹配和存储，可优先接 Nakama。
- TypeScript 实时状态同步和房间扩容，可优先接 Colyseus。
- 卡牌拖放、扇形手牌、动画和布局，可按目标客户端使用现有 UI 组件。

## 采购/采用前的 PoC 验证清单

不要只跑官方 Demo。给每个候选同一组 3–5 天测试：

1. 实现 10 张故意复杂的卡：多目标、延迟触发、替代效应、复制、随机、死亡触发、隐藏选择。
2. 用同一 seed 和命令序列重复 1,000 次，检查状态哈希是否完全一致。
3. 测试断线重连、超时托管、投降、观战和版本不一致。
4. 检查服务端是否能够独立验证所有客户端动作。
5. 检查旧对局日志在更新卡牌数据后能否重放。
6. 测量单进程并发对局数、单局内存、序列化体积和 10,000 局无头模拟耗时。
7. 核对许可证是否允许闭源、商店分发、服务器部署、团队多席位和二次分发。

建议评分权重：

| 维度 | 权重 |
|---|---:|
| 规则表达力与可测试性 | 25% |
| 确定性、回放、隐藏信息 | 20% |
| 服务端权威与联机完整度 | 20% |
| 可维护性、升级路径、文档 | 15% |
| 内容生产效率 | 10% |
| 许可与总成本 | 10% |

## 最终建议

短期若要验证“做出一款游戏”，采购并试跑 **TCG Engine、CCG Kit、Single-Player CCG Kit** 中符合玩法的一款，同时用 **boardgame.io** 做一个极简 Web 规则原型，能最快看出模板与自研之间的真实差距。

长期若要建设这个仓库所代表的“卡牌游戏引擎”，不要把目标设成另一个 Unity/Godot 场景模板。更有价值的方向是：**引擎无头、状态确定、规则可枚举、回放可验证、客户端无关、服务端权威**。现有 Unity/Godot 模板可以成为兼容层或示例客户端，而不应成为内核边界。
